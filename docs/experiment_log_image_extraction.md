# 이슈 #83 - 이미지·표 추출 방식 비교 실험 기록

## 배경

이슈 #68에서 PaddleOCR + 로컬 Qwen2.5-VL로 이미지를 처리했으나 다음 문제가 확인되었습니다.

- 워드클라우드를 `table`로 오분류하고, 실행할 때마다 판정이 달라짐
- 흐름도·구성도에서 요약 문장이 생성되지 않고 유형 단어만 출력됨

같은 이미지를 OpenAI 비전 모델로 처리했을 때 더 정확한지, 그 차이가 비용을 정당화하는지 실측으로 확인했습니다. 본문 텍스트 추출은 기존 방식을 유지하고 표와 이미지만 대상으로 했습니다.

## 비교 대상

`config/default.yaml`의 `multimodal.extraction_mode`로 선택합니다.

| 모드 | 글자 추출 | 유형 판정·요약 |
| :--- | :--- | :--- |
| `paddle_qwen` | PaddleOCR | Qwen2.5-VL-3B (로컬) |
| `paddle_openai` | PaddleOCR | OpenAI 비전 |
| `openai_only` | OpenAI 비전 | OpenAI 비전 (한 번의 호출로 함께) |

`paddle_openai`와 `paddle_qwen`은 글자를 동일한 PaddleOCR 결과로 씁니다. 두 방식의 차이는 유형 판정과 요약뿐이므로, 이 둘의 비교는 같은 입력 위에서의 순수한 모델 비교입니다.

## 표본 구성

VLM 대상 이미지 182장 중 15장을 골랐습니다. 이 작업의 목적이 표·서식의 구조 보존이므로 표 중심으로 구성하되, 오분류를 확인할 대조군을 넣었습니다.

| 유형 | 장수 | 포함 이유 |
| :--- | :--- | :--- |
| 표·서식 | 7 | 90도 회전 서식, 중첩 표(표 안의 표), 체크박스 서식 포함 |
| diagram | 3 | 흐름도, 네트워크 구성도 |
| chart | 1 | 대시보드 그래프 |
| photo | 2 | 항공사진, 지도 — 표로 오인하는지 확인 |
| logo | 1 | 대조군 |
| 전면 검정 이미지 | 1 | 없는 내용을 지어내는지 확인(환각 테스트) |

정답은 유형 판정은 15장 전부, 핵심 키워드는 원본 해상도로 직접 대조한 7장에 대해 작성했습니다. 키워드 대조 방식은 팀 공통질문(`data/evaluation/questions.jsonl`)의 채점 방식과 동일하게 맞췄습니다.

## 결과

### 1. 추출 모드 3종 비교 (동일 이미지 15장)

| 모드 | 유형 판정 | 키워드 적중 | 표 구조 보존 | 환각 | 비용 | 장당 시간 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `openai_only` | 93% (14/15) | 85% (47/55) | 5/7 | 없음 | $0.018 | 7.5초 |
| `paddle_openai` | 100% (15/15) | 62% (34/55) | 2/7 | 없음 | $0.008 | 12.2초 |
| `paddle_qwen` | 57% (8/14) | 62% (34/55) | 2/7 | 있음 | $0 | 12.9초 |

Qwen의 오분류 사례입니다.

- 지도 → `diagram` (정답 `photo`)
- 영향평가 결과서 → `table` (정답 `form`)
- 대시보드 그래프 → `other` (정답 `chart`)
- 전면 검정 이미지 → `diagram`. OpenAI는 두 모드 모두 `other`로 판정하고 "완전히 검은 화면으로 아무 글자나 사물이 보이지 않습니다"라고 답변

글자 추출은 흐름도에서 격차가 가장 컸습니다. 도형 안에 흩어진 글자를 `openai_only`는 12개 키워드 전부, PaddleOCR은 4개만 잡았습니다. 반대로 90도 회전된 서식에서는 PaddleOCR이 5/7, `openai_only`가 3/7로 회전 문서에서는 PaddleOCR이 나았습니다. 회전 문서 표본이 1장뿐이라 일반화하지는 않았습니다.

`paddle_qwen`은 3508×1181 이미지에서 메모리 부족으로 프로세스가 강제 종료되어 15장 중 14장만 처리했습니다. Qwen2.5-VL이 이미지를 원본 해상도로 토큰화하는데 리사이즈 상한이 없어 발생한 것으로, 182장 전량 실행 시 재현될 수 있습니다. OpenAI는 같은 이미지를 정상 처리했습니다.

### 2. 모델 비교 (gpt-5-mini vs gpt-5-nano, 동일 이미지 10장)

픽셀이 큰 순, 즉 토큰이 가장 많이 드는 10장으로 비교했습니다.

| 모델 | 입력 토큰 | 출력 토큰 | 비용 | 평균 응답 |
| :--- | :--- | :--- | :--- | :--- |
| gpt-5-mini | 31,114 | 4,539 | $0.0169 | 5.7초 |
| gpt-5-nano | 38,252 | 4,604 | $0.0038 | 5.2초 |

nano가 4.5배 저렴합니다. 다만 같은 이미지에 대해 입력 토큰을 22~23% 더 소비합니다. 모델별 이미지 토큰 환산 계수가 다르기 때문이며, 단가 차이가 커서 결론은 바뀌지 않습니다.

정확도에서 차이가 확인되어 mini를 채택했습니다.

- 표 구조 유지: mini 3/10, nano 1/10. nano는 유형을 `table`로 판정해놓고 셀 구분자를 넣지 않은 사례가 있음
- 오독: `세계 초월도시` → `세계로도시`, `유사사업 자료` → `유사업자 자료`
- 환각: 로고에서 글자를 `K R`로만 읽고 요약에 존재하지 않는 기관명(`한국철도공단`) 생성. 실제는 `국가철도공단`

182장 환산 시 mini $0.31, nano $0.07로 차이가 $0.24입니다. 표본이 가장 큰 이미지들이라 상한값이며, 이 규모에서는 비용이 선택 기준이 되기 어렵다고 판단했습니다.

### 3. `openai_only`의 한계

표를 읽기는 하지만 완전하지 않습니다.

- 체크박스 서식은 체크된 칸(■)과 안 된 칸(□)을 구분해 정확히 옮김
- 중첩 표는 표 안의 표까지 계층을 살림
- 다만 숫자를 오독함. `6.25 명` → `62.5일`, `50 개월` → `50.7월`

소수점 위치와 단위가 함께 틀렸습니다. 금액·기간을 근거로 답해야 하는 특성상 이미지 경로 결과는 검증이 필요합니다.

표 7장 중 구조를 살린 것은 5장이며, 90도 회전 서식과 전략체계도는 살리지 못했습니다.

## 결론

이미지 처리는 **`openai_only`, `gpt-5-mini`, `reasoning_effort: minimal`, `detail: high`**로 확정합니다.

- 유형 판정 93%, 키워드 85%, 표 구조 5/7로 세 방식 중 가장 정확
- 장당 7.5초로 가장 빠름
- 182장 처리 비용 $0.22 수준으로 이 규모에서 제약이 되지 않음
- 전면 검정 이미지에서도 없는 내용을 지어내지 않음

`config/default.yaml`의 `extraction_mode` 기본값은 `paddle_qwen`으로 두었습니다. 팀 협의 후 변경합니다.

## 적용 원칙

같은 표라도 파일에 어떤 형태로 저장돼 있느냐에 따라 꺼내는 방법이 다릅니다. 알아맞히는 방식보다 파일에서 꺼내는 방식을 우선합니다.

| 대상 | 방법 | 원리 |
| :--- | :--- | :--- |
| PDF 표(텍스트 레이어) | `pymupdf_find_tables` | 셀 좌표를 그대로 읽음. 오독 없음 |
| HWP 본문 표 | 레코드 직접 파싱 | `TABLE`·`LIST_HEADER` 레코드의 행·열 수와 셀 좌표를 읽음. 오독 없음 |
| 이미지(도식, 차트, 그림으로 된 표) | `openai_only` | 픽셀을 보고 알아냄. 오류 가능 |

이미지 경로는 파일에 글자 데이터가 없어 다른 방법이 없을 때만 사용합니다.


## HWP 표를 이미지 경로로 처리하지 않은 이유

HWP 본문의 표는 그림이 아니라 텍스트 레코드로 저장되어 있어 이미지 추출 대상(182장)에 포함되지 않습니다.
OCR이나 VLM으로 처리하려면 HWP를 PDF로 변환해 그림으로 만든 뒤 다시 인식해야 하는데, 이는 파일에 이미
저장된 좌표 정보를 버리고 추측으로 되찾는 방식입니다. 실제로 LibreOffice 변환을 시도했으나 내장 필터가
HWP 3.0만 지원해 5.x 문서를 열지 못했습니다.

정확도에서도 이미지 경로가 불리합니다.

| 방식 | 표 구조 보존 | 숫자 정확도 |
| :--- | :--- | :--- |
| `openai_only` | 5/7 | `6.25 명` → `62.5일` 오독 확인 |
| `paddle_qwen` | 2/7 | - |
| PyMuPDF | 698/740 (94%) | 저장된 값을 읽으므로 오독 불가 |
| HWP 직접 파싱 | 11,930건 전부 | 저장된 값을 읽으므로 오독 불가 |

규모도 고려했습니다. 청크 대상 HWP 표 8,830개를 이미지 경로로 처리하면 약 $10.6와 18시간이 필요하지만
직접 파싱은 비용 없이 몇 분에 끝납니다.

다만 이미지 실험에 포함된 표 7장은 모두 **그림으로만 존재해 파서가 접근할 수 없는 표**였습니다.
이런 경우에는 이미지 경로가 유일한 방법이므로 계속 사용합니다.

## 남은 과제
